## Основна думка

Доробляти слід цілісний цикл **досвід → осмислення → стійке розуміння → перегляд**.
Три шари вже мають потрібні ролі; недоведені місця — збереження змісту на переходах,
дозрівання узагальнень, зміна знання з часом та відбір для конкретної відповіді.
Додатковий шар зберігання або ще один постійно працюючий агент із цього не випливає.

Задум Archive ширший за таблицю фактів: він має зберігати причину, наслідок,
важливість і тон епізоду. Задум Core ширший за профіль: він має повільно накопичувати
обґрунтоване розуміння, залишаючись здатним переглядати свої висновки. «Людиноподібність»
тут означає вибірковість, тяглість і обережне узагальнення, а не довільне забування
або вигадування емоцій для красивої історії.

## 1. Зафіксувати різні ролі шарів

| Шар | На яке питання відповідає | Що не слід із нього автоматично робити |
|---|---|---|
| Session | Що відбувається зараз, хто що сказав і на що відповідає? | Поточну емоцію або разову репліку — постійною рисою людини |
| Archive | Що тоді сталося, чому це було важливо і звідки ми це знаємо? | Правдиве збереження чужого твердження — доказом правдивості самого твердження |
| Core | Що достатньо стійке й обґрунтоване, щоб впливати на майбутню взаємодію? | Стійкість — незмінністю; активне переконання — абсолютною істиною |

Нинішній стан від host — сьогоднішня локація персонажа, поточне завдання чи режим —
має лишатися явно поточним станом у context package. Він не стає пам'яттю лише
тому, що потрібен для цієї відповіді. Задані host-ом основи персони й навчені
висновки також мають різне походження; reflection не отримує права переписати
авторські правила персонажа або права доступу.

Для Session важливо розділити **надійно прийняти подію** та **показати її моделі**.
Стратегія просить раннє збереження важливого, бот — відсутність дубля поточного
повідомлення й вигаданої доставленої відповіді. Це сумісні цілі: прийнятий вхід,
згенерований результат і підтверджена доставка мають різні стани; кожна репліка
з'являється в діалозі один раз. Не пропонується просто переставити чинний ingest
перед генерацією. Конкретна crash-safe реалізація належить P2/DR-09.

## 2. Замкнути шлях змісту до осмислення

Спочатку використати те, що вже вміє бібліотека: Core request, query-aware Archive,
стабільну атрибуцію, повний асоціативний блок за opt-in. Це DR-01/03/11/12 у P3.
Без цього оцінка «пам'ять слабка» змішує якість двигуна з відкинутими host-ом даними.

Для reply потрібна компактна когнітивна проєкція: хто сказав цитоване, що саме
цитується, хто зараз просить це запам'ятати. Якщо оригінал уже є в frozen source,
зв'язок має дозволяти не дублювати його текст; якщо його немає — суттєвий зміст
повинен увійти в дозволену проєкцію явно. Точний формат визначається контрактом,
а не читанням довільного Telegram payload усіма проходами.

Archive має зберегти епізод як досвід, але **канонічні MemoryUnits залишаються
джерелом prompt-тексту**. Наратив може об'єднати підтверджені деталі й їхній
емоційний контекст. Відкинута або виправлена unit не повинна повертатися через
старий красивий gist. Не переносити в поточну розмову емоцію давнього епізоду
як теперішній стан людини.

## 3. Довести повільне дозрівання знання

Треба явно відрізняти два вже передбачені шляхи:

- **Прямі заяви людини про себе.** «Мене звати Олена», «Я переїхала до Львова»:
  явний/структурно перевірений personal-signal path може дати scoped Core-факт.
  Не потрібно змушувати людину повторити ім'я кілька разів. Це збережене твердження
  з атрибуцією і часом, а не незалежна перевірка зовнішнього світу.
- **Висновки пам'яті про людину.** «Її цікавить космос», «Вона уникає ризику»:
  це гіпотези, яким потрібні evidence, допустиме узагальнення й чинна процедура review.
  Один епізод або велике число confidence від LLM не дають права зробити їх Core.

Наявний graph storage — фундамент, а не доказ реалізованого мислення графом.
Доробка Phase 3 має навчити систему відрізняти:

`цікавить конкретна місія на Марс` → `цікавить дослідження планет` → `цікавить космос`.

Ширший висновок отримує слабшу підтримку від вузького епізоду. Одна розмова,
її підсумок, цитата й повторний переказ ботом не стають чотирма незалежними
доказами. Для maturation потрібна простежувана незалежність первинного досвіду,
а не тільки різні ID або кількість схожих речень. Не вводити універсальне
«три згадки — і факт»: прямота, різноманітність контексту й відстань узагальнення
мають різне значення.

Reflection має підсилювати або уточнювати ту саму гіпотезу, коли evidence це
виправдовує. `no_insight` — повноцінний успіх: «сьогодні я втомлена» може лишитися
епізодом без народження риси характеру. Пізніший показ спогаду самим ботом не
рахується новим користувацьким досвідом для reflection trigger.

## 4. Зробити знання змінюваним у часі

Потрібні різні наслідки для трьох випадків:

| Нова репліка | Інтерпретація, яку треба перевірити | Бажаний наслідок |
|---|---|---|
| «Я вже переїхала зі Львова до Києва» | Зміна стану з часом | Старе місце може лишитися правдивою історією; поточне — нове |
| «Я не казала, що живу у Львові; це була Оля» | Помилка атрибуції | Спірний факт перестає подаватися як безумовне актуальне знання; виправлення проходить контрольований шлях із джерелом |
| «Мене цікавить та місія на Марс, а не космос загалом» | Надмірне узагальнення | Широка гіпотеза звужується; вузький підтверджений інтерес не зникає разом із нею |

Це запланований temporal/dispute lifecycle, а не привід непомітно перезаписати
Core останньою реплікою будь-якого учасника групи. До рішення суперечність повинна
бути видимою як невизначеність, а не як дві одночасно безумовно істинні тези.
Хто має право підтвердити зміни — host policy; для Smartest review кандидатів
лишається DEC-040. Рішення не відкриває менеджеру приватні висновки про інших.

Уточнення доречне тільки при поверненні до теми, коли відповідь справді від нього
залежить. Наприклад: «Ти вже остаточно переїхала чи зараз тимчасово в Києві?»
Це майбутній opt-in механізм із обмеженнями частоти й повторів, не обов'язкове
опитування після кожного Sleep. Відповідь знову стає звичайною атрибутованою
подією, а не прямою довільною мутацією гіпотези від host-а.

## 5. Не змішувати різні оцінки спогаду

Частина таких оцінок уже є в схемах. Пропозиція — перевірити їхні ролі й
споживачів, не запровадити ще один набір дубльованих полів.

| Оцінка | Що означає | Чого не доводить |
|---|---|---|
| Fidelity | Стиснення чесно передає джерело | Джерело говорить правду про світ |
| Support | Наскільки обґрунтовано висновок із незалежного досвіду | Математичну ймовірність істини |
| Importance | Наскільки важливий епізод для цієї пам'яті | Що він доречний у кожній відповіді |
| Temporal validity | До якого часу/умов належить твердження | Що старе автоматично хибне |
| Relevance | Чи допомагає спогад відповісти зараз | Що він має потрапити в Core |
| Exposure | Скільки разів його вибирала сама система | Нове незалежне підтвердження або доведену користь |

Документи свідомо дозволяють recall feedback, тому повністю прибрати підсилення
за зверненнями означало б змінити задум. Натомість DR-13 ставить конкретне питання
калібрування: чи не переважає власний показ новий тематичний сигнал. Порівняти
bounded/decaying exposure-бонус, відбір без нього та сильніший вплив явного запиту
на тих самих історіях; жоден варіант чи коефіцієнт тут не оголошується прийнятим.

Ядро спочатку перевіряє scope, стан і придатність джерел, потім релевантність,
бюджет та дублікати. Вектори — опціональний шлях знайти давню доречну деталь.
Порожня асоціація при сторонній темі краща за обов'язковий «найближчий» спогад.
Модель має бачити різницю між давнім епізодом, Core, суперечністю й живим діалогом.

## 6. Завершити забування як частину того самого циклу

Слід зберегти відмінність між:

- менш доречним спогадом, який рідше вибирається;
- м'яко забутим спогадом із контрольованою можливістю повернення;
- відкинутою/спотвореною тезою, яка не може повертатися як факт;
- незворотним purge за волею користувача.

Значущі епізоди та джерела активного Core потребують спеціального захисту від
автоматичного decay/forgetting. Але цей захист не скасовує явного purge.
Якщо джерело визнано хибним або видалене, треба перевірити залежні гіпотези,
Core-підтримку, індекс і prompt-проєкції; коли підтримки бракує — позначити це
або відправити на перегляд. Не вимагати фізичного стирання всієї історії для
кожного зниження актуальності й не зберігати приховану копію після purge.

Для Smartest підключення maintenance/forget-review має бути окремим контрольованим
кроком: API в бібліотеці й реально запущена політика у host — різні речі.

## Порядок доведення без розростання проєкту

1. **Справний шлях інформації на поточному host.** P3 + потрібний text lifecycle P2:
   зміст, автор, запит, Core і асоціативна секція; без нового сховища або LLM-pass.
2. **Завершений v0.5 на реальних циклах.** Один кандидат, незалежне підсилення,
   challenge і no-insight; recovery без повторних effects. Поточні synthetic
   probes корисні одразу; старий validation PASS не переноситься на нові дані.
3. **Phase 3 maturation поверх існуючого graph storage.** Лише після чинного
   v0.5 gate; одночасно контрольний набір для relevance/exposure й меж узагальнення.
4. **Phase 4 час і виправлення.** Зміна факту, помилка автора та звуження висновку
   мають різні переходи, зі стабільними джерелами й історією рішення.
5. **Phase 5 уточнення, коли потрібне.** Opt-in, доречність, відсутність повторів;
   процедура підтвердження узгоджується з host privacy policy. Забування й
   інвалідація залежностей перевіряються на кожному попередньому етапі.

Когнітивна програма вже описана в wiki. Ця пропозиція уточнює її зв'язок із
контрприкладами Smartest; не створює конкурентний roadmap бібліотеки. Google Play,
PostgreSQL і server workers не є передумовою цих локальних перевірок та лишаються
окремим призупиненим напрямом згідно з прочитаним roadmap.

## Як відрізнити завершення моделі від додавання механізмів

| Послідовність досвіду | Очікуваний результат |
|---|---|
| Двоє однойменних людей, reply на чуже повідомлення, Sleep, нова Session | Збережено зміст, автора й того, хто звертався; у prompt є потрібний факт |
| Одна розмова про Марс, її переказ і повторний показ | Один первинний доказ, без автоматичного широкого переконання про космос |
| Незалежні розмови на споріднені теми | Пояснюване підсилення відповідної гіпотези, не купа її перефразувань |
| «Сьогодні втомилась», потім звичайний день | Епізод зберігся за потреби, постійна риса характеру не виникла |
| Переїзд / виправлення автора / заперечення узагальнення | Різні контрольовані наслідки; старий факт не подається безумовно як поточний |
| Після десяти показів сторонніх спогадів поставлено конкретне запитання | Потрібне знаходиться або нестачу даних видно; exposure не замінює релевантність |
| Topic switch із векторами та той самий сценарій без векторів | Стара асоціація не тягнеться далі; базова пам'ять працює в обох режимах |
| Forget/reject/purge джерела й повторне читання через усі шляхи | Застарілий gist/індекс не воскресає; залежні твердження мають коректний стан |

Це запропоновані критерії, не звіт про їх проходження. Вимірювати слід повноту
потрібних фактів у prompt, правильність атрибуції, зайві/надто широкі переконання,
застарілі твердження, доречність recall та вартість повного циклу. Кількість
створених Core-фактів чи виконаних reflection calls сама по собі не є успіхом.
Вартість порівнюється разом із якістю; вимкнення tracks або зміна моделей не
входять у цю пропозицію як уже дозволена оптимізація.
