# v0.6 Hypothesis Graph Storage: Chibigochi Acceptance

## Purpose

Перевірити на копії живої памʼяті Chibigochi, що коміт `c91b002` безпечно
переносить плоскі `candidate_belief.v1` у графове сховище, не губить
provenance, не вигадує звʼязків і не змінює поведінку звичайної розмови.

Це acceptance лише для Phase 2 storage foundation. Він не перевіряє якість
майбутніх ієрархічних узагальнень Mars → planets → space: їх ще не генерує
reflection, і вони належать Phase 3.

## Test target

- код бібліотеки: `c91b002` (`Add recoverable hypothesis graph storage`) або
  його descendant, у якому diff після `c91b002` є лише документаційним;
- execution path: Chibigochi live owner memory, не Telegram;
- міграція: тільки повна копія storage, зроблена при зупиненому Chibigochi;
- live storage: у цьому тесті не мігрувати;
- версія/tag: не піднімати, навіть після PASS.

## Hard rules

1. Не змінювати код, prompts, thresholds, storage records або очікувані
   результати під час прогону. Якщо є FAIL, зупинити відповідний сценарій і
   зафіксувати факти.
2. Перед копіюванням зупинити Chibigochi. Source storage не редагувати вручну
   й не використовувати для migration або fault injection.
3. Міграцію, повторну міграцію та адміністративний export виконувати на копії.
   Source не повинен отримати graph-migration writes. Два product-smoke
   повідомлення можуть створити звичайні session events; не запускати для них
   sleep або reflection і вказати цю очікувану зміну у звіті.
4. Не писати тексти приватних спогадів або candidate statements у постійні
   логи. Для доказів достатньо IDs, counts, hashes, scope, statuses і чисел.
5. `core_scope = null` означає тільки unscoped namespace, а не wildcard.
6. Міграція не має створювати semantic relations, abstraction levels,
   contradiction scores, validity windows або inferred directness.

## Preflight

1. Зафіксувати:
   - library commit і чистоту дерева;
   - якщо HEAD новіший за `c91b002`, підтвердити, що code/config diff від
     `c91b002` порожній, а відмінності стосуються лише документації;
   - Chibigochi commit і чистоту дерева;
   - шлях до активного `memory_engine` module, його mtime, size і SHA-256;
   - реальний owner scope та `host_id`, які використовує Chibigochi;
   - source storage path і test-copy path.
2. Зупинити Chibigochi, зробити повну копію storage, після чого source більше
   не використовувати в migration-сценаріях.
3. Після перевірки code diff зібрати поточний HEAD через
   `maturin develop --release` у тому самому Python environment, з якого
   працює Chibigochi. Перезапустити Chibigochi й повторно зафіксувати
   path/mtime/hash завантаженого module.
4. На test copy до міграції зняти:
   - кількість читабельних legacy candidates загалом і по `core_scope`;
   - кількість candidates за status;
   - кількість distinct cited MemoryUnit IDs, reinforcements і IDs, яких немає
     у storage;
   - кількість наявних graph nodes/evidence/relations;
   - SHA-256 кожного legacy candidate file.
5. Зберегти канонічний JSON результату `list_candidates()` до міграції. Для
   порівняння дозволено нормалізувати лише порядок списку за `candidate_id`;
   поля всередині records не викидати.

## Deterministic recovery control

До роботи з копією виконати:

```powershell
cargo test -p memory_engine --test engine_hypothesis
```

Цей suite є обовʼязковим fault-injection контролем: він повторно відкриває
`started` migration operation після втрати graph files, відновлює її без
дублювання, перевіряє CandidateBelief projection, graph-only fields і
cross-scope rejection. Не відтворювати цей crash ручним редагуванням живих
даних.

## Live-copy procedure

### 1. First migration

Відкрити test copy тим самим `host_id`, що використовує Chibigochi, і виконати
рівно один адміністративний виклик:

```python
result = json.loads(engine.migrate_hypothesis_graph())
```

Очікування:

- `schema_version == "hypothesis_graph_migration_result.v1"`;
- `source_candidate_count` дорівнює кількості читабельних legacy candidates;
- `relations_created == 0`;
- migration journal operation завершена, а не залишена `started`;
- warnings та `unresolved_memory_unit_ids` відповідають реальним відсутнім або
  нечитабельним records, а не замінені вигаданою provenance;
- hashes legacy candidate files не змінилися.

### 2. Exact-scope export and full mapping audit

Для кожного scope, знайденого серед legacy candidates, виконати:

```python
graph = json.loads(engine.export_hypothesis_graph(json.dumps({
    "schema_version": "hypothesis_graph_export_request.v1",
    "core_scope": scope,
})))
```

Окремо виконати export з `core_scope: null`. У сукупності всіх exact-scope
exports перевірити кожний legacy candidate, а не вибірку:

- існує node з `hypothesis_id == candidate_id` і
  `legacy_candidate_id == candidate_id`;
- `text/category/status/confidence` без втрат проєктуються у
  `statement/category/status/support_score`;
- timestamps, source sessions, archive IDs, MemoryUnit IDs, tags,
  reinforcements, promotion checks, review і promoted Core ID збережені;
- новий node не отримав вигаданих `abstraction_level`,
  `contradiction_score` або `validity`;
- усі migrated evidence links мають `polarity=supports`,
  `directness=legacy_unspecified` і не мають `generalization_distance`;
- на кожну distinct пару `candidate/hypothesis + cited MemoryUnit` існує один
  evidence link. Повторні reinforcement origins не перетворюються на кілька
  незалежних evidence links;
- для читабельного MemoryUnit link має `resolution=resolved`, а його
  `archive_id` і `source_session_id` збігаються з самим unit;
- для відсутнього або нечитабельного MemoryUnit link має
  `resolution=unresolved`, без вигаданих archive/session IDs;
- `relations` після legacy migration порожній.

Scope isolation:

- owner export не містить nodes іншого scope;
- `null` export містить лише unscoped nodes;
- export іншого наявного scope не містить owner nodes;
- якщо в dataset немає unscoped або другого scope, записати `DATASET GAP`, а
  не вигадувати fixture у копії. Cross-scope negative control уже зобовʼязаний
  пройти в deterministic suite.

### 3. Idempotence

Після першої міграції зняти hashes усіх graph node/evidence/relation files і
виконати `migrate_hypothesis_graph()` вдруге.

Очікування:

- `nodes_created == 0`, `nodes_updated == 0`;
- `evidence_links_created == 0`, `evidence_links_updated == 0`;
- unchanged counts відповідають уже матеріалізованим legacy records;
- `relations_created == 0`;
- graph file hashes і legacy candidate hashes не змінилися;
- зміна journal/manifest metadata між викликами не вважається зміною graph
  records.

### 4. Compatibility projection

Повторити `list_candidates()` після міграції та порівняти з preflight
snapshot. Після сортування за `candidate_id` канонічні records мають бути
рівними. Це доводить, що чинний v0.5 reflection/review API не змінився через
нове storage representation.

На другій disposable копії вже мігрованого storage тимчасово прибрати один
legacy candidate file, не чіпаючи graph node/evidence, і повторити
`list_candidates()`. Відповідний CandidateBelief має відновитися з graph
projection з тими самими v0.5 полями. Після перевірки цю копію відкинути; не
повертати такий стан у source storage.

### 5. Prompt and product regression

Міграція та export не повинні викликати LLM. За provider telemetry/logs
підтвердити нуль нових model calls під час цих адміністративних операцій.

Через звичайний Chibigochi `/v1/chat` виконати два smoke-запити:

1. запит про один відомий давній факт власника;
2. запит на сторонню тему, яка не потребує цього факту.

Перевірити тільки регресію:

- Chibigochi відповідає й використовує правильний owner scope;
- відомий факт доступний звичайним memory path;
- у сторонню тему він не протікає;
- у context package або rendered prompt немає окремого hypothesis-graph
  блока, graph relations чи технічних evidence records.

Стиль відповіді моделі та якість ієрархічного узагальнення тут не є gate.

## Verdict rules

`IMPLEMENTATION PASS` дозволений лише якщо одночасно:

- завантажено module, код якого відповідає `c91b002`;
- deterministic recovery control пройшов;
- усі legacy candidates перевірені без втрати полів;
- evidence cardinality і resolved/unresolved provenance правильні;
- migration створила нуль semantic relations;
- повторна migration не змінила graph records;
- legacy files лишилися незмінними;
- exact-scope isolation виконана;
- CandidateBelief compatibility projection виконана;
- migration/export не викликали LLM і graph не потрапив у prompt.

Будь-який lost field, invented provenance/relation, duplicate evidence,
cross-scope record, незавершений journal, неідемпотентний повтор або зміна
legacy source є `IMPLEMENTATION FAIL`.

`PRODUCT REGRESSION PASS` оцінюється окремо. Він не може перетворити storage
FAIL на PASS. Відсутній live приклад unresolved unit чи другого scope —
`DATASET GAP`, якщо відповідний deterministic control зелений.
